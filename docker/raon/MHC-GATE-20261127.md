# Native Raon mHC gate candidate

The opt-in FlyDSL path removes the two Torch chart GEMMs and two FP32 copies
per mHC site, together with the existing Triton head/mix. It uses two native
kernels: head/chart/aggregate, then residual/branch mix. The validated AITER
HIP projection and FlyDSL split-reduction finisher remain unchanged. The gate
equation is Raon's chart, not AITER's different Sinkhorn gate.

```bash
export RAON_ROCM_MHC_BACKEND=hip
export RAON_ROCM_MHC_FINISHER=flydsl
export RAON_ROCM_MHC_GATE=flydsl
```

The default remains `legacy`. The new path accepts BF16 `[T,4,2560]` on gfx950,
preserves the BF16 projection-score and branch/output boundaries, and performs
the gate/chart in FP32. Unsupported native configurations fail explicitly.
No attention, expert quantization/packing, model weights or graph-mode defaults
were changed. The full MXFP4 model was not benchmarked in this round.

## Mathematical and graph checks

Slurm 89526, TheraC80, eight independent GPU fixtures. The final all-layer run
passed **2,400 cases and 100 weight-refit/replay checks**, covering all 25 layers,
attention and MLP sites, T=1/4/5/8/32/256/1024/16384, input scales .125/1/8,
identity/affine branches and both `RAON_BATCH_INVARIANT` modes. Both branch
forms were also screened on layers 0/1/12/24 in the initial 432-case run.

The independent Torch reference uses FP32 math with the checkpoint's BF16
parameter, GEMM-score, branch-input and output rounding boundaries retained.
Checks include branch input, post/residual coefficients, final output, the
existing native projection plus legacy gate, the fully legacy implementation,
changed-input graph replay, and refit of phi, alpha, bias and eta. Original
weights are restored after refit. Captured parameter-buffer pointers stayed
stable; repeated execution was exact. With batch invariance enabled, every
tested full block was bit-identical across batch sizes.

Worst relative RMS errors against Torch gold were **0.0529% for output**,
**0.0649% for aggregate**, **0.00608% for coefficients**, and **0.0565% for
changed-input replay**. Output versus the existing production block was
**0.00804%**. The unchanged screen requires finite values and both RMS error
at most `1e-5 + .01 * reference_rms` and peak error at most
`1e-5 + .02 * reference_peak`. This is component correctness evidence, not
a full accuracy evaluation or proof for every possible input.

A real GPU trace contains only the HIP projection, `finish_0.kd`, `head_0.kd`
and `mix_0.kd` for an identity-branch site. The chart GEMMs/copies and Triton
mHC head/mix are absent. The existing HIP/FlyDSL packages were not patched.

The block-only graph screen, excluding compilation and warmup, measured about
**1.44–1.53x at T1** and **1.90–1.94x at T32** with an identity branch across
four real sites. It excludes attention/MLP computation and is not output TPS.

| --- | ---: | ---: | ---: | ---: |

These are single-trial observed ratios, not isolated compute gains. In
particular, SD-off C32 generated 53,089 versus 69,911 tokens; different natural
lengths and occupancy affect throughput. The workload is not the official
prompt reproduction or the separate fixed ISL/OSL benchmark. Measured token
prefix-hit ratios were 0% except SD-on C32 (4.05% for both gates), **not 50%**.
No MMLU-Pro or other new full accuracy score is claimed.

SD acceptance length `1 + delta(accepted drafts) / delta(draft steps)` was
3.452 -> 3.478 at C1 and 3.564 -> 3.532 at C32. C1 therefore supplies no
evidence of an end-to-end gain despite the faster mHC block. The candidate
remains opt-in rather than becoming a universal default.

## Retained failures and next investigation

The initial compiler attempt defined variables only inside FlyDSL branches;
initializing the values before the branches fixed the compilation failure.
The first parallel diagnostic step mistakenly requested 8GB of host memory
and hit its cgroup limit; the subsequent step used full allocated memory and
passed. An old SD-on-only client demanded a draft witness for SD off; those
four cases stopped before measurement and were rerun with that check corrected.
No successful performance condition was measured twice. All failed attempts
remain in the raw evidence.

For the SD-on C1 follow-up, inspect draft metadata construction and graph
scheduling before another arithmetic rewrite. The actual server reports that
`ROCM_RAON_DFLASH` cannot update draft decode metadata in place and rebuilds
it eagerly. Its builder also runs CPU `diff().tolist()`. This is a concrete
candidate to profile, not a measured attribution or an instruction to set the
capability flag without implementing capture-safe metadata refresh. Accepted
counts, state indices and cache-write lifetime must remain correct.
